# ТендерПульс — API трекера этапов выполнения заказов

Бэкенд для агентства, которое ведёт закупки и тендеры по поручению клиентов.
Заказ клиента проходит фиксированный пайплайн этапов, менеджер ставит задачи исполнителям,
система следит за сроком каждого этапа и уведомляет участников о сменах этапа и просрочке.

Кейс собран по реальному заказу с фриланс-биржи («Мобильное приложение мониторинга этапов
выполнения заказов», $2000): постановка задач в работу, информирование о стадиях и сроках,
обмен информацией с исполнителями. Требования к интерфейсу вынесены в
[`ТЗ_для_дизайнера.md`](ТЗ_для_дизайнера.md), а этот репозиторий — серверная часть для
мобильного и веб-клиента.

## Что внутри

- **Ноль зависимостей** — только стандартная библиотека Node.js, ESM (`"type": "module"`).
- `src/app.js` — ядро: домен, права доступа, маршруты. Про HTTP не знает ничего.
- `server.js` — тонкий HTTP-адаптер на `node:http` (порт из `process.env.PORT`, по умолчанию 3000).
- `test/app.test.mjs` — 16 тестов на `node:test`, ядро вызывается напрямую, порт не поднимается.
- Данные: JSON-файл `data/store.json` (создаётся при первом запуске, в git не попадает).
- Пароли хранятся только в виде scrypt-хеша с солью (`node:crypto`), в открытом виде — нигде.

## Запуск

```bash
node server.js          # http://localhost:3000
PORT=4000 node server.js
```

Проверка вживую:

```bash
curl -s -X POST http://localhost:3000/api/login \
  -H "Content-Type: application/json" \
  -d '{"email":"anna@tenderpulse.ru","password":"tenderpulse"}'

curl -s http://localhost:3000/api/orders?overdue=1 -H "X-Token: <токен>"
```

Корневой адрес `GET /` отдаёт карту API со списком всех маршрутов и демо-учёток.

## Этапы заказа

Пайплайн фиксированный:

```text
new (Новый) → in_progress (В работе) → on_review (На проверке) → done (Выполнен) → closed (Закрыт)
                                                                        ↘ cancelled (Отменён)
```

Правила переходов (`POST /api/orders/:id/stage`):

- вперёд — на следующий этап пайплайна;
- назад — на предыдущий, но обязательно с `reason` (причина возврата);
- в `cancelled` — с любого незакрытого этапа и только с `reason`;
- из `cancelled` — только в `new` (восстановление заказа), тоже с `reason`;
- переход на тот же этап, прыжок через этап, любой переход из `closed` — ошибка (400/422/409);
- без явного `stageDueDate` новый этап получает срок через 5 дней.

Каждая смена этапа пишет запись в историю заказа и уведомляет исполнителя и менеджера заказа
(кроме того, кто сам изменил).

## Эндпоинты

Все ответы — JSON (`Content-Type: application/json; charset=utf-8`). Авторизация — заголовок
`X-Token: <токен из /api/login>`. Ошибка всегда `{ "error": "текст на русском" }`.

### Авторизация

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/login` | вход по почте и паролю, выдаёт токен |
| `POST /api/logout` | выход, токен удаляется из хранилища |
| `GET /api/me` | текущий пользователь по токену |

```bash
curl -s -X POST localhost:3000/api/login -H "Content-Type: application/json" \
  -d '{"email":"maxim@tenderpulse.ru","password":"tenderpulse"}'
# {"token":"5f0c…","user":{"id":"u2","name":"Максим Орлов","role":"manager","roleTitle":"Менеджер",…}}
```

### Сотрудники

| Метод и путь | Назначение | Кто |
| --- | --- | --- |
| `GET /api/users` | список с числом активных и просроченных заказов | админ, менеджер |
| `POST /api/users` | создание сотрудника (`name`, `email`, `role`, `position`, `password` от 6 символов — обязателен) | админ |
| `PATCH /api/users/:id` | правка профиля; почта и роль — только себе и только админом | админ, сам сотрудник |
| `DELETE /api/users/:id` | удаление; 409, если у исполнителя есть активные заказы | админ |

Правила, которые стоит знать: id пользователей, клиентов и заказов не переиспользуются (счётчик идёт дальше после удалений); тело запроса больше 1 МБ отклоняется с `413`; неверный JSON — `400`.

### Клиенты

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/clients?q=&status=` | список с агрегатами: заказов, активных, просроченных, сумма бюджета |
| `POST /api/clients` | создание (`name` обязателен) |
| `GET /api/clients/:id` | карточка клиента вместе с его заказами |
| `PATCH /api/clients/:id` | правка полей и статуса (`active`/`archived`) |

### Заказы

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/orders` | список с фильтрами (см. ниже) |
| `POST /api/orders` | создание: `title`, `clientId`, `stageDueDate` обязательны |
| `GET /api/orders/:id` | карточка: заказ, комментарии, история, `nextStages`, права |
| `PATCH /api/orders/:id` | правка полей: название, описание, клиент, менеджер, бюджет, сроки |
| `POST /api/orders/:id/assignee` | назначение/снятие исполнителя (`executorId` или `null`) |
| `POST /api/orders/:id/stage` | смена этапа: `stage`, `reason`, `stageDueDate` |
| `DELETE /api/orders/:id` | удаление вместе с историей и комментариями, только админ |

Параметры списка: `stage=`, `executorId=`, `managerId=`, `clientId=`, `overdue=1`,
`soon=1` (срок этапа в течение 3 дней), `due=week` (общий срок в течение недели),
`scope=mine`, `q=` (номер, название, описание, название клиента), `sort=stageDue|created|amount`.

### Уведомления

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/notifications` | все уведомления пользователя + счётчик непрочитанных |
| `POST /api/notifications/:id/read` | отметить одно прочитанным |
| `POST /api/notifications/read-all` | отметить все |

Типы: `assigned` (назначили заказ), `stage` (сменился этап), `deadline` (изменили срок),
`comment` (новый комментарий), `due_soon` (срок этапа ≤ 2 дней), `overdue` (этап просрочен).
Последние два не хранятся в базе, а считаются на лету по текущему сроку этапа,
поэтому не бывает «зависших» уведомлений о просрочке у закрытых заказов.

## Чего в MVP осознанно нет

- **Настоящей авторизации по JWT/refresh-токенам.** Токен случайный и лежит в хранилище: для
  одного сервера и демо-стенда этого достаточно, для нескольких инстансов нужны подписанные токены
  и общий Redis.
- **Загрузки файлов.** Вложения — только ссылки на внешнее хранилище, загрузка и антивирус — вне MVP.
- **Истории изменений по всем полям.** В историю попадают этапы, срок этапа, исполнитель,
  менеджер, клиент и вложения, но не каждое исправление описания.
- **Push-уведомлений и рассылок.** Уведомления живут внутри приложения (таблица + расчёт по срокам),
  мобильные push — отдельная задача с FCM/APNs.
- **Клиентского портала.** Клиенты есть как справочник, но входа для них нет: по ТЗ заказчика
  обмен информацией идёт с исполнителями, а не с заказчиками.
- **Планировщика.** Напоминания о сроке считаются в момент запроса, отдельного воркера с cron нет.
- **Пагинации.** Для 24 заказов она не нужна; на реальных объёмах — первый шаг оптимизации.
- **Регистрации.** Сотрудников заводит администратор, саморегистрации нет (по ТЗ заказчика).
